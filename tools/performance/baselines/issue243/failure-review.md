# Routing continuation failure review

The review followed capture through engine preparation, worker delivery, view/MCP ownership and the final `Session::change` transaction. No peer, UI thread or worker waits on a result-channel send. Native queues share two worker permits with DRC, each owner keeps one running job and at most one replacement, and typed prepared edits cannot be constructed from MCP JSON. GUI owners retain one additional ready result and reusable immutable pad projection.

Tests exercise source replacement/reopening, session mismatch, rule edits, Undo, out-of-order prepared edits, pointer replacement, Escape, focus/input epoch, layer/size/view mismatch, concurrent MCP mutations, one-step Undo, unchanged saved bytes before publication, no-op pointer identity, original short and lock regressions, real native copper execution, a full native pool, disconnected worker channels, expired/revoked/modal MCP requests, a full deferred MCP slot and a real client disconnect. Existing rendered replay asserts route/layer/cancel behavior and concurrent native MCP edits; browser replay uses the shared command without native transport.

Code inspection additionally covered thread spawn failure, worker unwind and poisoned projection state: worker permits use RAII, sender loss produces a terminal error, the projection lock is only attempted without waiting, and failed preparation produces no candidate. Application teardown signals cancellation without joining. The socket acceptor and individual peers remain independently bounded; after authentication, peers sample disconnect/stop at up to 20 ms intervals. Authentication and frame I/O retain their original two-second deadlines. A disconnect racing a transaction already authorized by the editor cannot be made atomic across the socket boundary.

Candidate construction and final history publication remain linear phases bounded by supported model limits; native workers move preparation off the UI, while browser scheduling yields between engine batches and phases. The nominal browser polling allowance is a tuning choice, not a hard deadline. Raw phase, polling, publication and cancellation measurements are retained alongside standard replay reports. Process RSS collection includes startup and correctness work and does not attribute isolated allocations to the new queues.

Existing CPU report schema 1 retains its legacy unmeasured labels for strict before/after comparability. In particular, the background-queue label refers to measurements absent from that report; the separate route/checker lifecycle reports supply those measurements. Neither CPU nor GPU-readback reports establish physical presentation latency or qualify the recorded overnight Wayland stall.

The broad replay showed transient slowdowns in unchanged UI and tessellation work as well as the changed path. This does not isolate job cost. Both the 100-sample runs and a sequential repeat are retained without attributing those tails to the routing scheduler. The final pointer handoff reuses the exact resolved path already painted, removing a second pad projection. A targeted ten-iteration CPU replay and native rendered replay were collected after that change; the final native rendered comparison was refused because observed focus/visibility transitions differed. The additional broad browser rendered repeat was stopped rather than chasing that comparison. Earlier rendered comparisons passed their identity checks on the preceding candidate. Job-specific diagnostics, independent correctness regressions and source fingerprints are the basis for the routing lifecycle conclusions. None of these data qualify #237's full editor latency targets.
